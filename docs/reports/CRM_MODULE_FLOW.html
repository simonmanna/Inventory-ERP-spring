How the CRM module works

Data model, business process, data flow between modules, and screen-to-screen UI flow of the CRM as it runs on main 5e6fce34 (after the 2026-11-22 review fixes). Written from the Spring backend, the React web client and the database schema.

1Overview

The CRM turns an enquiry into revenue: capture a lead, qualify it into an opportunity, move it through configurable pipeline stages with planned activities, quote it, get the quote approved, and convert it into a sales document. After the sale, complaints and service requests are handled as cases.

Salesperson

Works own pipeline

Creates leads, schedules calls and meetings, moves cards on the kanban, writes quotations.

Sales manager / team lead

Sees the team

With crm:deal:view_all (or as team leader) sees everyone's deals, targets, reports and forecasts.

Approver

Releases quotes

Approves quotes that break the discount cap, the amount threshold or the credit check, manually or via an approval workflow.

Customer service

Handles cases

Owns complaints and service requests with a due time set by priority; cases can come from delivery discrepancies.

2Data model

One Deal table holds both leads and opportunities, told apart by kind. Its status (open, won, lost) is separate from its pipeline position (stageId). Quotations belong to the sales module and point back at the deal.

3Process & workflow

Four connected lifecycles: the deal, the quotation, the activity and the case.

3.1 Lead to won deal

stateDiagram-v2
  direction LR
  [*] --> Lead : New lead
  Lead --> Lead : edit, schedule activity
  Lead --> LeadLost : Mark lost (reason)
  LeadLost --> Lead : Reopen
  Lead --> Opportunity : Convert (create customer / link / none)
  [*] --> Opportunity : New opportunity (customer required)
  state Opportunity {
    direction LR
    New --> Qualified
    Qualified --> Proposition
    Proposition --> Negotiation
    Negotiation --> Qualified : drag back
  }
  Opportunity --> Won : Mark won / quote converted (auto-win)
  Opportunity --> Lost : Mark lost (reason + note)
  Lost --> Opportunity : Reopen
  Won --> Opportunity : Reopen
  1. Capture.A lead needs only a name; company, contact, phone and expected amount are optional. The owner defaults to the creator and must be a user of the organisation.
  2. Qualify and convert.Convert creates a new customer from the lead's company, links an existing customer, or links none. The record becomes an opportunity in the chosen stage and crm.lead.converted is published. A lead cannot be moved on the pipeline or marked won before conversion.
  3. Work the pipeline.Dragging a card (or the stage bar on the detail page) moves it; each move writes a history row and a stage-change activity, and publishes crm.deal.stage_changed. Probability comes from the stage unless overridden, so weighted value = amount × probability.
  4. Close.Won stamps wonAt, makes the partner a customer, publishes crm.deal.won. Lost records a reason and note. A won deal must be reopened before it can be marked lost.

3.3 Activities

Scheduled from a deal, a customer, the kanban card badge or the Activities page. Each has a type (call, email, meeting, task, note), due time, optional reminder and assignee. The planner groups them as overdue today upcoming done. Marking done records an outcome and can schedule a follow-up in the same step; a note is done the moment it is logged. The kanban card shows the next activity's state, so a deal "going cold" is visible without opening it.

Updates, assignment and status changes lock the case row, and a delivery discrepancy can open at most one case (advisory lock), so double clicks and parallel edits cannot fork a case.

4Data flow

Every screen talks REST to /api/v1. Controllers check permissions, services run one transaction per action, and events leave through the transactional outbox only after commit.

  UI->>UI: refetch crm-suite queries (dashboard, lists, 360)

6Access rules

Permissions

crm:lead:read|write, crm:deal:read|write|view_all, crm:activity:read|write, crm:quotation:read|write|approve|convert, crm:case:read|write, crm:pricing:read|manage, crm:report:read, crm:dashboard:read, crm:configure.

Record visibility

Without crm:deal:view_all a user sees deals they own, unassigned deals, and deals of teams they lead. Hidden records answer 404, on the new routes and on the legacy /crm/deals routes alike.

Shared lookups

Stages, teams, tags and sources load for anyone holding any CRM read permission, so a case-desk or lead-only user still gets working dropdowns.

Tenancy & audit

Every query is filtered by organisation. Creates, edits, archives and restores are written to the audit log and shown in each record's history.
